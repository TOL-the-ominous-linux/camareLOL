# camareLOL 1.0.1 — Beta 2

**Released:** 26 October 2026  
**Status:** beta / pre-release  
**Tag:** `v1.0.1`  
**npm:** `@wenker-ai/camarelo@beta` — the `latest` tag deliberately stays on `0.1.22`

camareLOL is a safety-first TUI installer for Arch Linux. This is the second
beta. It fixes two defects found while testing the published 1.0.0 one-liner
on a normal installed machine. No planning, partitioning, `pacstrap`,
bootloader, desktop, safety-gate, IPC or config-schema behaviour changed.

---

## 1. What went wrong in 1.0.0

### Virtual block devices were offered as disks

`lsblk` labels `zram0`, `ram0`, `nbd0`, `md0` and `loop0` as type `disk`.
camareLOL trusted that label and listed them on the Storage screen. On the
packaging host, `/dev/zram0` appeared as a **4 GiB SATA SSD**.

The immediate effect was noisy: `--self-test` picked zram as the empty disk,
tried to plan a root that needs at least 8 GiB, failed, and printed
`self-test: FAILED` on a host where nothing was wrong.

The dangerous effect was conditional: a zram device larger than the planner's
minimum would have passed size validation. The plan would then have targeted
volatile memory instead of a disk. Planning into RAM and calling it an install
is not a failure mode this project is willing to leave in place.

### `--self-test` ran the simulated install on the wrong disk

After checking for an empty disk, the self-test used `devices.first()` for the
simulated install. On an installed machine that is the disk holding the running
system, not the empty target. The simulation came back incomplete and the
self-test reported FAIL.

The simulated install needs a disk it is allowed to format. If there is no
empty disk, the honest result is “skipped”, not “failed”.

## 2. What changed in 1.0.1

- Discovery ignores `zram*`, `ram*`, `nbd*`, `md*`, `dm-*`, `loop*` and `fd*`.
  Real disks, virtio disks (`vd*`, `xvd*`), NVMe, MMC and USB devices are
  unchanged.
- `--self-test` runs the simulated install on the empty disk it already found,
  and prints `skipped (no empty disk)` when there is none.
- A regression test feeds `lsblk` JSON containing zram, ram, nbd, md, loop and
  a real disk; only the real disk is returned.
- The Rust suite is 329 tests: 281 in `camarelol-core`, 48 in the TUI crate.

The host safety check is unchanged: an unvalidated distribution is still
refused, and `--self-test` still fails on one. That is the intended result.

## 3. Evidence

- `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
  and `cargo test --workspace`: **329 passed** (281 core + 48 TUI).
- Python tests, the Java catalog tests, and the three acceptance scenarios
  (empty disk, Windows disk, partition without a filesystem) passed.
- On the packaging host, `--self-test` now reports:

  ```console
  1. devices discovered: 2
     - /dev/sda SATA SSD — 119 GiB | GPT | 2 partitions
     - /dev/nvme0n1 NVMe SSD — 477 GiB | GPT | 2 partitions
  2. no empty disk to plan for (skipped)
  6. simulated install: skipped (no empty disk)
  selftest result: PASS
  self-test: OK
  ```

  Before the fix the same host discovered three devices (including zram0),
  failed the zram plan, and exited 1.
- GitHub Actions on `main` is green, including the corrected Ubuntu smoke test
  that asserts camareLOL **refuses** an unsupported host.
- **VM acceptance was not rerun for 1.0.1.** `VBoxManage` is not installed on
  the packaging host, so `scripts/make-release.sh` was run with `SKIP_VM=1`.
  The change is in discovery and the self-test, not in any disk-writing phase;
  the previous VM evidence still describes the write path. This is still a
  skipped gate, and it is disclosed here rather than hidden.

## 4. Install 1.0.1 beta

The beta is **opt-in**. The default one-liner and `npm install -g` continue to
resolve the newest **stable** release (0.1.22).

### From GitHub Releases (pre-release)

```console
$ curl -fsSL https://raw.githubusercontent.com/tamkogay9876-code/camareLOL/main/scripts/camarelol.sh \
    | CAMARELOL_VERSION=v1.0.1 bash
```

```console
$ curl -fsSL https://raw.githubusercontent.com/tamkogay9876-code/camareLOL/main/scripts/camarelol.sh \
    | CAMARELOL_CHANNEL=beta bash
```

Both paths download the binary, check the ELF magic, verify it against the
release `SHA256SUMS`, require `--version` to agree with the tag, and then run
`--self-test`.

By hand:

```console
$ curl -fLO https://github.com/tamkogay9876-code/camareLOL/releases/download/v1.0.1/camarelol
$ curl -fLO https://github.com/tamkogay9876-code/camareLOL/releases/download/v1.0.1/SHA256SUMS
$ sha256sum -c SHA256SUMS
$ chmod +x camarelol
$ ./camarelol --self-test
$ sudo ./camarelol
```

### Via npm (beta tag)

```console
$ sudo pacman -S --needed nodejs npm curl
$ npm install -g @wenker-ai/camarelo@beta
$ camarelol --version
```

The npm package bundles the 1.0.1 binary.

### From source

```console
$ git clone https://github.com/tamkogay9876-code/camareLOL
$ cd camareLOL
$ ./install.sh
$ ./build.sh test             # Rust + Python + Java + acceptance scenarios
```

## 6. Upgrading from 1.0.0

Replace the binary. The configuration schema is still version 1, so saved
profiles load unchanged. There is no automatic update path, by design:

```console
$ curl -fsSL https://raw.githubusercontent.com/tamkogay9876-code/camareLOL/main/scripts/camarelol.sh \
    | CAMARELOL_VERSION=v1.0.1 bash
```

Via npm:

```console
$ npm install -g @wenker-ai/camarelo@beta
```

Rolling back to the first beta:

```console
$ curl -fsSL https://raw.githubusercontent.com/tamkogay9876-code/camareLOL/main/scripts/camarelol.sh \
    | CAMARELOL_VERSION=v1.0.0 bash
```

## 7. Known limitations

The limitations in the [1.0.0 release notes](1.0.0.md#8-known-limitations)
still apply. In particular:

- Three Stage 2 items remain partial: model-keyed GPU driver suggestions,
  VM observation of the NetworkManager configuration, and VM observation of
  stale-firmware cleanup.
- NTFS resize, dual-boot beside a real Windows installation, manual
  partitioning, LUKS and Btrfs subvolume layouts are deliberately deferred.
- The installer still runs only on Arch Linux with systemd. Other
  distributions are refused at plan time.

## 10. Warning

Installing an operating system and partitioning disks **can destroy data**.
camareLOL asks before every irreversible step, re-identifies the disk before
writing, and never claims success it did not verify. Still: back up anything
you care about, and run it from a live ISO rather than on the machine you are
trying to fix.
