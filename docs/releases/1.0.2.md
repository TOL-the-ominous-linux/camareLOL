# camareLOL 1.0.2 — Beta 3

**Released:** 28 October 2026  
**Status:** beta / pre-release  
**Tag:** `v1.0.2`  
**npm:** `@wenker-ai/camarelo@beta` — the `latest` tag deliberately stays on `0.1.22`

camareLOL is a safety-first TUI installer for Arch Linux. This beta fixes the
last misleading output the 1.0.1 self-test could produce on a machine
camareLOL does not support, and adds first-hand evidence from a real
Arch-in-QEMU run. No planning, partitioning, `pacstrap`, bootloader, desktop,
safety-gate, IPC or config-schema behaviour changed.

---

## 1. What went wrong in 1.0.1

### An unsupported host printed `self-test: FAILED`

Running `--self-test` on Ubuntu 24.04 (Google Cloud Shell) printed:

```
0. host detected: Ubuntu 24.04 LTS, unknown init system
   supported: false
   REFUSED: distribution "ubuntu" is not one camareLOL has been validated on.
...
selftest result: FAIL
```

That FAIL said the tool was broken. It was not: every machinery check on that
host passed — discovery found the devices, the safety gate stayed closed, the
configuration round trip was `ok`. What failed was the host gate, by design.
A test that reports design as a defect teaches the user to ignore it.

---

## 2. What changed in 1.0.2

- `--self-test` now reports three outcomes with distinct exit codes:
  - `PASS` — exit 0: all checks passed.
  - **`SKIP (host unsupported)` — exit 2**: the machine is not one camareLOL
    supports. The machinery checks still ran above the host line, and they
    passed. This says nothing bad about the tool.
  - `FAIL` — exit 1: a machinery check failed wherever it runs. Report that.
- The FAIL branch wins over SKIP: a broken safety gate on a strange distro is
  still a bug, not an environment question.
- Exit codes are documented in the quick-start page (all three languages).

## 3. Proof from a real run (Arch 7.2.7 in QEMU/KVM, 20 GiB empty `-qcow2`)

`v1.0.1` assets, downloaded inside the VM from the canonical organisation URL:

```
0. host detected: Arch Linux / systemd
   supported: true
1. devices discovered: 1
   - /dev/vda SATA HDD — 20 GiB | no partition table
2. UEFI -> 2 partitions (root: true, esp: true, table: GPT) ok
2. BIOS -> 2 partitions (root: true, esp: false, table: GPT) ok
4. safety gate refuses formatting by default: true
5. configuration round trip: ok (archlinux)
6. simulated install: completed (12 phases)
selftest result: PASS
```

The TUI opened on the same console and closed cleanly (`Ctrl-C`): Welcome
shows `v1.0.1+3b0c356`, firmware `UEFI`, host `Arch Linux / systemd`, network
`OK` and `Disks: 1 detected`. In a VM everything writes to a qcow2 file —
nothing outside it is touched.

*Known cosmetic quirk from that session: the discovery JSON labels a virtio
disk `kind: "SataHdd"` even though `transport` says `virtio`. Timing for
`1.0.3`, no effect on planning.*
