# camareLOL 1.0.0 — Beta 1

**Released:** 26 October 2026  
**Status:** first beta / pre-release  
**Tag:** `v1.0.0`  
**npm:** `@wenker-ai/camarelo@beta` — the `latest` tag deliberately stays on `0.1.22`

camareLOL is a safety-first TUI installer for Arch Linux. It detects the
hardware, proposes a layout, shows the exact plan, and writes to a disk only
after the user types a confirmation phrase. It is not a shell wrapper: the
installer has its own pipeline — discovery → plan → review → confirm →
execute → verify — with a safety gate in front of every destructive step.

This is the first beta. It is the same installer code as 0.1.22, re-versioned
and re-documented after a full roadmap audit. No installer behaviour changed in
1.0.0; what changed is the release identity, the documentation, and the
tooling that publishes and verifies releases.

---

## 1. Why 1.0.0 is a beta

The roadmap is now complete in the only sense this project accepts: every item
is either **shipped with evidence**, explicitly marked **partial**, or
deliberately **deferred with a written reason**. A checkbox is not proof; a
VirtualBox run or a real-machine run is.

Three Stage 2 items are still partial, and two storage features are explicitly
deferred. They are listed in [Known limitations](#8-known-limitations) below.
Calling this release beta is not modesty — it is the accurate label for a
1.0.0 whose remaining gaps are known and documented instead of hidden.

The version number is now `1.0.0` because the feature set is frozen enough to
deserve a stable number. It does **not** mean "safe on every disk". The warning
in the README still applies: install on an empty disk, from the Arch live ISO,
with a backup.

## 3. What is new in 1.0.0

### Release identity

- The Cargo workspace, `Cargo.lock`, npm package, PKGBUILD template and
  dual-boot helper now agree on **1.0.0**.
- The binary is built from tag `v1.0.0` and reports
  `camareLOL 1.0.0 (tag v1.0.0, commit …)`.
- The GitHub release is published as a **pre-release**; npm is published under
  the **`beta`** dist-tag. `npm install -g @wenker-ai/camarelo` still installs
  0.1.22 until the beta is promoted.

### Documentation

- New canonical English release notes: this file.
- The README now describes the beta status, the beta install paths, the safety
  model and the known gaps without claiming the project is finished.
- The English, Vietnamese and Chinese documentation landing pages were updated
  for 1.0.0: stale "alpha" wording, the removed `u` update key, and the old
  "layout UI comes in Stage 3" claim are gone.
- The roadmap now points at 1.0.0 as the current release and keeps the partial
  and deferred items visible.
- The npm package page was rewritten for the beta and explains the `beta` tag,
  the bundled binary, and how to verify it.

### Release tooling

- `scripts/upload-release.sh` reads the release body from
  `docs/releases/<version>.md` instead of hard-coding one release's notes, and
  accepts `--prerelease`. Draft-then-upload-then-publish is unchanged, so a
  broken upload never leaves a half-published release visible.
- `npm/build.sh` accepts `NPM_TAG` (for example `NPM_TAG=beta`) and passes it
  to `npm publish`; the package is still packed only after the downloaded
  binary matches the release `SHA256SUMS` and reports the expected version.
- `scripts/camarelol.sh` accepts `CAMARELOL_CHANNEL=beta` to resolve the newest
  release including pre-releases; `CAMARELOL_VERSION` still pins an exact tag.
- `scripts/dual-boot-auto.sh` pins the beta channel and refuses builds older
  than 1.0.0.
- `install.sh --binary` now verifies the downloaded binary against the release
  `SHA256SUMS` and accepts `CAMARELOL_VERSION` to install an exact release.
- `scripts/make-release.sh` finds a JDK through `JAVA_HOME` (the same logic as
  `build.sh`) and documents the `SKIP_VM=1` decision in its output.

### No installer behaviour changes

There are no changes to discovery, planning, partitioning, `pacstrap`, fstab,
bootloader, desktop profiles, the safety gate, the IPC protocol or the config
schema. A profile saved by 0.1.22 loads unchanged.

## 4. What the installer does

- Detects disks, partitions, filesystems, EFI partitions, Windows, recovery and
  Microsoft-reserved partitions, and live-system mounts.
- Plans GPT and MBR layouts: ESP, BIOS boot, `/`, `/home`, swap, with ext4,
  btrfs or xfs, validated against the firmware mode.
- Detects Windows and refuses to touch it.
- Installs a minimal Arch system: pacstrap, fstab, bootloader (GRUB or
  systemd-boot), locale, keymap, timezone, hostname, users, sudo policy,
  services and initramfs.
- Offers seven desktop profiles: KDE, GNOME, Xfce, Cinnamon, LXQt, Hyprland and
  Sway; Wayland or X11 with compatibility checks; SDDM, GDM, LightDM or greetd.
- Handles PipeWire, PulseAudio or neither; Bluetooth, zram and swap choices;
  NetworkManager; and a conservative set of drivers and firmware.
- Supports package search and selection, AUR packages built as a normal user
  (never as root), and saved/resumed configuration profiles.
- Exports a redacted diagnostics report with `--save-diagnostics <FILE>`.
- Speaks Vietnamese, English and Simplified Chinese (`--lang vi|en|zh`).
- Implements keep-everything dual-boot: a GPT+UEFI disk keeps every existing
  partition as `format=false`, reuses its ESP at `/boot/efi`, and appends the
  new partitions inside the largest aligned free gap with
  `sgdisk --new=…`. There is no zap and no partition-table rewrite.
- On a dual-boot plan, installs GRUB on the reused ESP, enables os-prober and
  writes `GRUB_DISABLE_OS_PROBER=false` in the bootloader phase, before
  `grub-mkconfig`.
- Deletes only stale firmware boot entries whose loader file is missing from
  **our** ESP, matched by GUID; `FvFile`/`CdRom`/`Usb` devices and other
  partitions are never touched. A broken `efibootmgr` listing skips the
  cleanup instead of failing the install.

### Safety model

- Locked by default. `--allow-destructive` opens the gate; `--execute` is
  required to write; the Review screen still demands a typed `ERASE` or
  `ERASE AND WIPE`.
- `--preview` runs all twelve phases with every real command printed and
  nothing executed. It ignores `--allow-destructive` and `--execute`, and a red
  banner stays on screen for the whole run.
- The disk identity is re-checked immediately before every write.
- Secrets are redacted from logs; configuration profiles never contain
  passwords.
- The binary has no self-updater, no index URL and no code path that replaces
  itself. Updates are a manual download or a package manager.

## 5. Evidence behind this release

- **VM acceptance:** the full harness last ran 7/7 on the 0.1.18 build; the
  dual-boot harness ran seven times, with run 7 producing 17 green checks
  (2026-10-22). It proves the fake Windows markers survived, the new root
  landed on a new partition, GRUB stayed on the original ESP, os-prober was
  installed, and the generated `grub.cfg` contained a Windows Boot Manager
  entry.
- **Real machine:** on 24 October 2026, `scripts/dual-boot-auto.sh` ran from a
  live ISO on a real 119 GiB GPT disk. The 1 GiB ESP and the 69 GiB
  EndeavourOS root stayed `format=false`; a ~49 GiB `camarelol-root` ext4
  partition was placed in the gap left by the deleted first partition. The
  first boot was confirmed: F11 → `camareLOL` → GRUB from `EFI/CAMARELOL/` on
  the reused ESP → Arch kernel → initramfs → desktop login.
- **Still pending on that machine:** booting EndeavourOS back through the
  generated `endeavouros (EFI BootNext)` GRUB entry, the `efibootmgr -o` default
  order swap, and the stale-entry/ISO cleanup listed in the roadmap.
- **Not rerun for 1.0.0:** the VirtualBox acceptance gate. VirtualBox is not
  installed on the packaging host, so the release was built with
  `SKIP_VM=1`; `scripts/make-release.sh` prints that skip instead of hiding
  it. Since 1.0.0 contains no installer logic changes over 0.1.22, the
  previous VM evidence still describes the same code path. This is a
  packaging and documentation release, and it is labelled beta accordingly.

## 6. Install 1.0.0 beta

The beta is **opt-in**. The default one-liner and `npm install -g` continue to
resolve the newest **stable** release (0.1.22).

### From GitHub Releases (pre-release)

Pin the tag, or ask for the beta channel:

```console
$ curl -fsSL https://raw.githubusercontent.com/TOL-the-ominous-linux/camareLOL/main/scripts/camarelol.sh \
    | CAMARELOL_VERSION=v1.0.0 bash
```

```console
$ curl -fsSL https://raw.githubusercontent.com/TOL-the-ominous-linux/camareLOL/main/scripts/camarelol.sh \
    | CAMARELOL_CHANNEL=beta bash
```

Both paths download the binary, check the ELF magic, verify it against the
release `SHA256SUMS`, require `--version` to agree with the tag, and then run
`--self-test`.

By hand:

```console
$ curl -fLO https://github.com/TOL-the-ominous-linux/camareLOL/releases/download/v1.0.0/camarelol
$ curl -fLO https://github.com/TOL-the-ominous-linux/camareLOL/releases/download/v1.0.0/SHA256SUMS
$ sha256sum -c SHA256SUMS
$ chmod +x camarelol
$ ./camarelol --self-test
$ sudo ./camarelol
```

### Via npm (beta tag)

```console
$ sudo pacman -S --needed nodejs npm curl
$ npm install -g @wenker-ai/camarelo@beta
$ camarelol --version
```

The npm package bundles the 1.0.0 binary. Its wrapper can still offer a newer
GitHub release when one exists; the binary itself never replaces itself.

### From source

```console
$ git clone https://github.com/TOL-the-ominous-linux/camareLOL
$ cd camareLOL
$ ./install.sh                # builds and installs to /usr/local/bin
$ ./build.sh test             # Rust + Python + Java + acceptance scenarios
```

### From the source tarball (`makepkg`)

Each release ships a `PKGBUILD` pinned to the released tarball's SHA-256:

```console
$ VERSION=1.0.0
$ curl -fLO "https://github.com/TOL-the-ominous-linux/camareLOL/releases/download/v$VERSION/camarelol-$VERSION.tar.gz"
$ curl -fLO "https://github.com/TOL-the-ominous-linux/camareLOL/releases/download/v$VERSION/PKGBUILD"
$ tar xf "camarelol-$VERSION.tar.gz"
$ cp PKGBUILD "camarelol-$VERSION/"
$ cd "camarelol-$VERSION"
$ makepkg -si
```

The `PKGBUILD` attached to the release is the generated one; the copy inside
the tarball cannot contain the tarball's own checksum, so use the attached
file.

## 7. Verify the download

Every GitHub asset is covered by `SHA256SUMS`:

```console
$ sha256sum -c SHA256SUMS
camarelol: OK
camarelol-1.0.0.tar.gz: OK
camarelol-catalog.jar: OK
PKGBUILD: OK
```

The binary also identifies itself:

```console
$ ./camarelol --version
camareLOL 1.0.0 (tag v1.0.0, commit …)
```

A binary that says `[built from a dirty working tree]` is not a release, no
matter what version it prints.

## 8. Known limitations

These are the honest edges of 1.0.0. They are documented in
[`docs/en/roadmap.md`](../en/roadmap.md), not hidden.

**Partial Stage 2 items**

- **Model-keyed GPU driver suggestions.** CPU microcode hints and a base set
  (`mesa`, `linux-firmware`) are selected from the host. GPU models are parsed
  from `lspci -mm -nn` into `GpuInfo.model`, but there is no driver suggestion
  keyed off the model yet (for example, an NVIDIA variant choice).
- **NetworkManager configuration.** The package is installed, the unit is
  enabled, and `/etc/NetworkManager/conf.d/00-camarelol.conf` pins
  `dhcp=internal`. This is unit-tested but has not yet been observed in a VM.
- **Stale firmware boot-entry cleanup.** Implemented and unit-tested with a
  VBox-shaped `efibootmgr -v` listing; VM observation is still pending.

**Deliberately deferred**

- **NTFS resize.** The acceptance criteria and safety checks are written down,
  but the feature is not built. Shrinking a partition that holds somebody's
  only Windows install is one-way and has no undo.
- **Dual-boot beside a real Windows.** The keep-everything side and the Windows
  menu entry are done and VM-proven with a fake Windows. What remains is what
  only real Windows can answer: observing the menu entry actually boot Windows,
  and the shrink-from-inside-Windows procedure. Do not point camareLOL at a
  disk that holds your only Windows install.
- **Advanced storage:** manual partition editor, LUKS encryption and Btrfs
  subvolume layouts have no code.

**Host policy**

- The installer runs on Arch Linux with systemd. Parabola, Hyperbola, Artix,
  Nyarch and `ID_LIKE=arch` derivatives such as EndeavourOS are refused at plan
  time, before a byte is written. That is deliberate: an unvalidated host with
  a different package set is not a safe target for an installer that erases
  disks.

## 9. Upgrading and downgrading

- **From 0.1.x:** replace the binary. The configuration schema is still
  version 1, so saved profiles load unchanged.
- **npm:** `npm install -g @wenker-ai/camarelo@beta` installs this beta;
  `npm install -g @wenker-ai/camarelo` installs the stable `latest` (0.1.22).
- **Rolling back:** install the previous tag explicitly:

  ```console
  $ curl -fsSL https://raw.githubusercontent.com/TOL-the-ominous-linux/camareLOL/main/scripts/camarelol.sh \
      | CAMARELOL_VERSION=v0.1.22 bash
  ```

There is no automatic update path, by design. See
[`docs/en/update.md`](../en/update.md).

## 12. Warning

Installing an operating system and partitioning disks **can destroy data**.
camareLOL asks before every irreversible step, re-identifies the disk before
writing, and never claims success it did not verify. Still: back up anything
you care about, and run it from a live ISO rather than on the machine you are
trying to fix.
